# 保真制作、分部装配与交付

## 先锁定标准

记录原图、用户认可的风格参考、认可的模型版本、各自 SHA256，以及用户选择的原话。用户说“这版最好”只表示选定继续修改的基准，不等于严格验收通过。指代不明确时只澄清一次，先做不依赖版本选择的整理。

后续修改另建候选；保留基准不变。原图约束元素和姿势，已认可的风格参考约束角色造型与材质；若二者冲突，沿用用户已明确接受的转换，关键冲突再询问。不能重新生成一张更容易建模的参考后，悄悄以它替代标准。退回旧版本须说明是回退，不能称为新生成或新精修。

## 选择表示方式与制作路线

- 高斯：适合可旋转的视觉重建。清晰的正面、高点数或 .blend 文件不证明可编辑人物网格、骨骼或碰撞已经存在。
- 网格：用户要求可编辑角色、精雕、动画或 GLB 时，应制作真正带表面的网格。检查实际对象、材质、纹理和渲染；排除原始点属性、抽样椭球代理、照片卡片。文件扩展名不作为完成证据。
- 混合：可同时保留高斯环境与网格角色，但清单逐件写明表示、用途和坐标；交付能力按实际最弱环节说明。

复杂场景一次生成后，人物脸、手、细字通常比分部近景更容易丢失。检查后端实际输入分辨率与细节预算，不猜测固定数值，不把增加点数当作保真保证。风格转换先统一整个人物的造型和材质，再考虑重建；动画角色不能贴回写实照片脸。

当整景细节不足，优先将同一照片内部拆成人物组、头部、衣装、手、道具、地面、植被等必要部件；拥抱、背负等相互接触的人物应共享姿势基准。内部拆分不等于将不同照片合并，也不改变最终一图一场景。不要机械规定每次必须六块；按实际元素选择。

高斯转网格只能作为候选底稿。体积重建可能出现凹坑、浮粒、孔洞、五指融合、过度膨胀或粗糙材质。闭合、无非流形边、面数很高仍可能视觉不合格。发现这些问题须重拓扑、补面或重新构建连续表面，不能把体素合并结果宣称手工精雕完成。

## 装配时保留造型

为每个部件记录坐标轴、单位、原点、前向、变换和来源。核对实际相机尺寸、视角、裁切和模型哈希；不同版本或不同分辨率的标注不能混用。

完整头部使用稳定解剖锚点与身体对接：头宽、眼线、下巴、颈根、肩线、衣领。自动关键点拟合只给初值，必须检查正面和侧面，防止头变小、夸张俯仰、双头残影和悬空。清除旧头前保护头发、衣领、围巾和附近手臂；颈根和衣领需要真实接合表面，不靠遮挡截图证明接合。

脸型、眉眼、笑容和牙齿不能因为“清晰”就判为与参考一致。手部检查指节连续、可见手指数量、指间空隙、手腕接合、托举和搭肩的实际接触。服装分别核对轮廓、衣领、袖口、层次、褶皱、围巾走向、裤靴与身体穿插。

## 分部设计审看

用户要求分部看时，可以展示基准局部、独立三维部件和待制作设计，但逐项明确区分：

- 图片或参考局部；
- 整体模型的局部放大/截取；
- 独立三维高斯部件；
- 独立可编辑网格部件；
- 尚未建模的设计方案。

设计板配合可操作的部件旋转入口。基准裁图或局部放大不能冒充新制作的独立网格；说明哪些造型保留、哪些结构待修，以及最终如何组成一个完整场景。用户要求看分部，可以撤销此前对中间展示的限制，但不自动授权发布或上传。

## 验证与展示

结构检查与视觉检查分别记录，不互相代替。建议检查 reference_fidelity、scene_coverage、identity_pose、style_consistency、assembly、multiview、interaction；无人物/无交互等不适用项须有理由。视觉检查写具体观察、检查者、候选哈希与实际视角证据。相似度、轮廓 IoU、关键点误差只用于定位问题；阈值要说明对齐和尺度，不能作为艺术验收的唯一依据。

在同一造型参考与相机条件下核对正面，再查看左右侧、斜面、背面、俯视及关键部位近景。检查 Blender 实际渲染，不能用网页高斯效果替代网格材质验收。核对材质槽、材质索引、颜色属性、UV、贴图打包和光照，避免白模、噪点、重复烘焙明暗或近邻取色污染。背侧属于推测，记录其合理性，不能宣称与未拍到的真实结构一致。

用户要求“验收通过后再看”时，候选、截图和渲染放在 work/ 等内部工作目录；不要主动嵌入中间图、给模型下载链接、更新成品入口或替换已选基准。先运行 scripts/check_delivery_review.py REVIEW.json。用户明确请求过程审看时可用 review_requested 模式，写入请求原话，清楚标注尚未通过，不据此宣布成品完成。

只认可实际观察过的视角和部位。不能沿用旧版证据批准新候选，不能为结束任务降低标准或无限承诺必然达到。未通过项继续修复；能力或资料确有缺口时如实说明，不谎称后台仍持续工作。

### 交付检查记录格式

REVIEW.json 的 candidate、style_reference 均为含 path、sha256 的文件记录；baseline_locks 为同类记录数组。路径相对 REVIEW.json 所在目录。requested_representation 与 actual_representation 使用 gaussian、mesh 或 hybrid，描述本次待展示物；分部设计审看不能据此把最终项目的网格要求降为高斯。

checks 按上述七个检查名填写。每项 status 为 pass、fail、unreviewed 或 not_applicable。pass 项必须含 reviewer、observation、candidate_sha256 和 evidence；evidence 为实际截图/核验文件的 path、sha256 数组。not_applicable 需 reason；参考一致、场景覆盖、风格一致、多视角不得省略。未做检查用 unreviewed，不能占位写 pass。

delivery_policy 默认 final_only；只有用户明确要求过程审看才设 review_requested，并填写 review_requested_by_user=true 和 user_instruction 原话。脚本退出码0表示允许按标注用途展示，退出码2表示阻止展示；始终读取 final_quality_approved 和 review_only，不能把允许看草稿当作成品批准。脚本只检查记录和证据完整性，不能判断观察内容是否真实。

## 外部服务与案例边界

“只用本机”按当前任务执行，不能暗中上传新服务。已有上传许可不能扩展到新提供方、素材或付费额度；确需改变时先说明具体目的、素材、目的地和费用。风格、禁止上传、暂停某案例等只在用户指定的范围生效，不能变成技能所有未来任务的硬编码偏好。技能代码包不含案例私照、个人关键点、三维资产、账号配置或本机运行库。发布遵守当前用户决定，不因更新技能自动上传 GitHub。
